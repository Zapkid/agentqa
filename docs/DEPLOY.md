# Deploying the VeroniQA public demo

The public demo is VeroniQA on its own URL (<https://veroniqa.vercel.app>):

| path | what |
|---|---|
| `/` | the home page: header and footer, the narrated introduction video (captions burned in), features, how it works, usage and cost charts, the technology behind it and the FAQ |
| `/talk/` | the VeroniQA app (Streamlit): chat, knowledge, test runs |
| `/videos/veroniqa-intro.mp4` | the video itself, served with range requests so it streams and seeks |
| `/robots.txt`, `/sitemap.xml`, `/llms.txt` | for search engines and AI assistants (see below) |
| `/index.md`, `/privacy`, `/privacy.md`, `/talk.md` | Markdown twins and the privacy page (see below) |
| `/.well-known/security.txt`, `/site.webmanifest` | security contact (RFC 9116) and the web app manifest |
| `/api/v1/...` | the public API: status, results, `POST /api/v1/ask` (cited answers from the demo documents) and the demo API's spec |
| `/openapi.json`, `/openapi.yaml` (also under `/api/`) | the public API's OpenAPI 3.1 description |
| `/.well-known/api-catalog` | the API catalog (RFC 9727): a linkset pointing to the OpenAPI, the guide and the status endpoint |
| `/developers`, `/developers.md` | the developer portal: quickstart, keys (none), endpoints, errors, rate limits, sandbox, CLI |

`/watch` (the home page's earlier address) and `/talk` redirect to the right place. Only the
introduction is hosted; the three short promo films stay in the repository (`media/videos/`). The
video is a plain `<video>` on the home page rather than inside the Streamlit app, where it did not
play on Vercel.

One ASGI app serves all three: `agentqa/veroniqa/server.py` wraps the Streamlit script in
Streamlit's `st.App`, moves Streamlit under `/talk/` (its `server.baseUrlPath`) and adds the home
page and video routes. It runs as a container image on Vercel
(`Dockerfile.vercel`). A plain Python function would not do: the locked dependencies are about
830 MB installed (Streamlit and pyarrow, Chroma and its runtime), and the app needs a WebSocket
for the life of a session.

## Discoverability (search engines and AI assistants)

The home page and its companions are generated by `agentqa/veroniqa/site.py` from data in the
repository (the subtitles, the video length), so they carry no claims the repo cannot back:

- One `<h1>`, semantic sections (`header`, `main`, `section`, `footer`), a skip link, a canonical
  URL, a description, Open Graph and Twitter card tags with the poster frame and the video.
- Structured data (JSON-LD): `WebSite`, `SoftwareApplication`, `VideoObject` (with duration,
  thumbnail and the full transcript) and `FAQPage`.
- The video transcript in the structured data and in `llms.txt` (the page itself shows the video
  with burned-in captions).
- The usage and cost charts (cost per run by strategy, tokens by stage, repeat runs with memory) are
  plain HTML and CSS bars with a table view each, in `charts.py`; a test recomputes every number
  from the latest `results/*.json`.
- The hero's six result tiles (bugs found, relative cost, performance defects caught and so on) are
  checked against the latest `results/*.json` by a test, like the README's Results section.
- `robots.txt` explicitly allows the major search and AI crawlers (GPTBot, OAI-SearchBot,
  ClaudeBot, PerplexityBot, Google-Extended, Applebot-Extended and others) and points to the
  sitemap; `sitemap.xml` includes a video entry; `llms.txt` is a plain-text summary for language
  models.
- **Agent readiness** (the checks behind scores such as is-agentic.com): every page has a
  Markdown twin, served for `Accept: text/markdown` with a single `Vary: Accept` header and a
  `Link: <...>; rel="alternate"; type="text/markdown"` header, and at its `.md` address. Unknown
  addresses get a real 404 (HTML or Markdown) that points to the home page, `llms.txt` and the
  sitemap; this includes `/talk/<anything>`, where Streamlit would otherwise answer 200 with its
  app shell. The `/talk/` shell itself gains a real title, a description and a `<noscript>`
  summary (`AgentFriendlyTalk` in `server.py`). robots.txt carries a Content Signals line, and
  there is a privacy page, a security.txt and an author in the structured data.
- **The public API** (`agentqa/veroniqa/public_api.py`, a FastAPI app mounted at `/api`) answers
  from the same simulated demo agent as the app. It needs no key; each client gets 60 requests a
  minute (10 for `/v1/ask`), reported with the IETF `RateLimit-Policy` and `RateLimit` headers.
  Every error, including unknown paths and wrong methods under `/api`, is an RFC 9457
  `application/problem+json` document with a stable `code` and a `hint`, and each code has an
  anchor in the developer portal (its `type`). The OpenAPI document is generated from the code, so
  it cannot drift; every page links to it (`Link: rel="service-desc"`, `rel="api-catalog"`), and
  the developer portal (`devportal.py`) builds its endpoint and error tables from it.
- **The CLI** (`clients/veroniqa-cli`, the `veroniqa` command) is a standard-library-only Python
  package. It installs from the repository today
  (`pipx install "git+https://github.com/Zapkid/agentqa#subdirectory=clients/veroniqa-cli"`);
  `make cli` builds the wheel. Publishing it to PyPI needs a PyPI account (see the end of this page).
- `VERONIQA_SITE_URL` sets the absolute address used in all of these (default
  `https://veroniqa.vercel.app`).

## What "hosted mode" changes

`Dockerfile.vercel` sets `VERONIQA_HOSTED=1`, which turns the local tool into a safe public demo
(`agentqa/veroniqa/hosted.py`):

- **Private, temporary workspaces.** Each visitor gets their own projects and vector stores,
  named by a random id kept in the page URL (`?w=...`). Reloading or sharing that link brings the
  same workspace back while the server instance lives; idle workspaces are deleted after 12 hours.
  A new workspace starts with the Orders API demo project and its documents.
- **Simulated models only.** The server holds no API keys, so a visitor cannot run up a bill.
- **Test runs only against the bundled Orders API**, at most two at a time. A public server that
  ran generated tests against any URL a visitor typed could be used to send traffic to other
  people's APIs, so the project settings for external APIs are locked and the run function
  refuses non-demo projects.
- Uploads (5 MB, type allowlist), link fetching (public addresses only) and the injection scan
  work exactly as they do locally.

Storage is the container's temporary disk. Workspaces do not survive a new deployment or a cold
start. This is a demo, not a place to keep work.

## One-time setup on Vercel

1. In the Vercel dashboard, **Add New → Project**, import the GitHub repository `Zapkid/agentqa`,
   and name the project **`veroniqa`**. That name gives the production URL
   `veroniqa.vercel.app` when it is free.
2. Leave the root directory as the repository root. Vercel finds `Dockerfile.vercel` there and
   builds the image; no build command, environment variables or secrets are needed.
3. Deploy. From then on every push to `main` deploys to production, and every other branch gets a
   preview URL.
4. If `veroniqa.vercel.app` is not assigned automatically, add it under **Settings → Domains**.

The image runs as an unprivileged user, listens on `$PORT` and writes only under `/tmp`.

## Keeping Vercel's image storage small

Vercel stores the container image of every deployment (each push to `main` and each branch
preview), so storage grows by one image per push until old deployments expire or are removed.
Two things keep it down:

- **A small image.** `Dockerfile.vercel` builds in two stages, so uv, its download cache (as big
  as the environment, about 830 MB) and the build layers are not shipped, and it uninstalls the
  packages the website never uses: locust and matplotlib (only `agentqa perf` and `agentqa eval`
  use them), and kubernetes and onnxruntime (Chroma dependencies for its distributed server and
  default embedding model; VeroniQA embeds locally). That took the image from about 2.1 GB to
  about 0.9 GB. The build ends with `import agentqa.veroniqa.server`, so if the app ever starts
  needing one of those packages the build fails instead of the deployment. Compiled bytecode
  (141 MB) is kept for faster cold starts; set `UV_COMPILE_BYTECODE=0` to trade that for size.
- **Expiring old deployments.** In the Vercel dashboard, **Settings → Security → Deployment
  Retention**, set short retention for preview, canceled and errored deployments (production is
  kept as the rollback target). Existing old deployments can be removed with
  `vercel remove <deployment-url>` or from the project's Deployments page; the images are freed
  with them. The tooling in this repository cannot do either, they need your Vercel account.

## Keeping Fluid function CPU and memory low

Vercel bills the function's *Active CPU* time. What drove it, and what is done about it:

- **An open tab reconnected forever.** Vercel closes a WebSocket when its function reaches the
  plan's maximum duration (5 minutes on Hobby), and Streamlit's page reconnects by itself: it
  fetches `/_stcore/health` and `/_stcore/host-config` at once (so two cold instances start),
  opens a new WebSocket and runs a new session. A tab left open in the background did that every
  5 minutes, for as long as it stayed open, which on a free plan's CPU allowance adds up to weeks
  of CPU. `idle_guard.py` is a small script in the `/talk/` page: when the connection drops while
  the tab is hidden, or untouched for 2 minutes, it holds back Streamlit's retry requests and
  shows a one-line notice; the first click, key press, scroll, touch or return to the tab reloads
  the page for a fresh session. Someone actually using the app reconnects as before.
- **Cold starts imported Chroma (about 1.1 of 1.8 CPU-seconds)** even for requests that never use
  it (pages, API status, health checks). It is now imported when the first vector store opens, so
  a cold start for those requests costs about 0.85 s instead of 1.8 s.
- **Every request woke the function.** Vercel's CDN caches a function's response only when it
  carries `s-maxage` (plain `max-age` is for browsers). Pages, Markdown twins, `robots.txt`,
  `sitemap.xml`, `llms.txt`, the OpenAPI files, the API catalog and `/404`s now send it (1 hour;
  a day for the video, the poster and Streamlit's hashed assets, about 70 files for a first
  visit). The `/talk/` app page and `/talk/_stcore/host-config` are cacheable too. Not cached:
  the API (its rate-limit headers are per client), `/talk/_stcore/health` and anything else that
  sets a cookie. A change can take up to an hour to reach a cached page.
- **Two cold instances per visit became one.** Streamlit's page requests `/_stcore/health` and
  `/_stcore/host-config` at the same moment, and when no instance is warm each request starts its
  own. `host-config` is the same JSON for every visitor and sets no cookie, so the CDN now answers
  it. `health` is deliberately not cached: it hands each visitor their own XSRF cookie, and a
  cached copy would share one visitor's cookie with everyone (the cache helper also refuses to
  touch any response that sets a cookie).
- **Streamlit's source-file watcher** is switched off in hosted mode (it starts per session in
  development to reload on save; a container's files never change): about a third less CPU per
  new session.

**Provisioned memory** (360 GB-hours a month on the free tier) is metered over how long an
instance exists, not how much it computes. Measured on production: one tiny request starts an
instance that stays until about 5 minutes after its last request (04:24:50 start, 04:29:55
shutdown), and an open WebSocket keeps it for the whole connection. So memory is spent by (1) how
many cold starts there are and (2) anything that touches the function more often than every 5
minutes, which keeps one instance alive around the clock (2 GB x 24 h = 48 GB-hours a day). The
caching above attacks both: repeat requests, crawlers and uptime checks are answered by the CDN for
an hour, and a visit starts one instance instead of two or three. The memory size itself is not
configurable on the free tier.

To check the effect, watch Active CPU under the project's Observability tab; on Hobby, runtime
logs are kept for one hour only. A cold start shows as `Started server process` in the logs.

## Run the same thing locally

```bash
make veroniqa-hosted     # hosted mode on http://127.0.0.1:8502 (home page with the video; app at /talk/)
make veroniqa            # the normal single-user app on http://127.0.0.1:8501
```

## Publishing the CLI to PyPI (needs the owner's PyPI account)

The name `veroniqa` was free on PyPI when the CLI was written. To publish: create the project on
PyPI with a trusted publisher for this repository (PyPI → Publishing → add a GitHub publisher),
then build and upload with `make cli` and `uv publish clients/veroniqa-cli/dist/*`, or from a
tagged GitHub Actions job using the trusted publisher. After that, `pipx install veroniqa` works
and the developer portal's install line can be shortened.
